## §1 Purpose & legal basis

ToS §2 and Privacy Policy §12 state that children under 13 play only through a parent-managed family group and that parents can review and delete the child's data. COPPA (16 CFR 312) requires, once the operator has actual knowledge a user is a child: (a) no behaviorally targeted advertising and no persistent-identifier collection for ad personalization; (b) no public discoverability or stranger contact; (c) verifiable parental consent obtained **before** collection; (d) parental review/deletion rights and cessation of collection when consent is withdrawn; (e) data minimization and bounded retention.

The 2026-08 code audit (15-agent, adversarially verified) established: the app is at minimum mixed-audience; **no child concept exists anywhere** in code; and beyond the child gap, several app-wide practices independently fail COPPA/data-minimization muster (silent login geolocation, contact identifiers on the peer-readable user doc, ad-ID-capable analytics defaults, zero retention limits, incomplete deletion). This SRS remediates all Critical- and High-risk audit findings.

The mixed-audience conclusion is an **accepted owner position, not merely an audit finding**. The cheaper alternative was put on the table explicitly — move `LSApplicationCategoryType` off `public.app-category.family-games`, retire the Family/Captain/Scout ladder for audience-neutral constructs, shift art direction off the cartoon-animal avatars, and raise the age rating — and the owner rejected it in favour of full compliance. Those child-directedness signals are therefore **deliberately retained** and are not to be "cleaned up" (D-16).

## §2 Execution model

### 2.1 Workflow (approved process)

1. Each feature (§3) is implemented by a subagent in an **isolated git worktree** off current `feature/MVPPush` HEAD. The main working tree stays untouched during development.
2. **Serialized landing — exactly one feature in the repo working tree at a time.** When the slot is free: rebase onto HEAD, apply to the working tree, verify build + focused tests, notify the owner with summary/files/results.
3. **Ready-to-test precondition (amended).** An agent MUST NOT tell the owner a feature is testable until every Firestore-rules and Cloud-Functions change in it is (a) **deployed to the dev Firebase project** and (b) **shown to the owner as the actual rules/function diffs**. The landing message carries a dedicated "backend changes (deployed)" section naming what was deployed.
   - *Originally specified:* step 2 ended at "verify build + focused tests, notify the owner" — an agent satisfying it literally hands over a build whose backend behaviour is still the old one in dev, and the SRS never mentioned deploying or disclosing rules/function diffs at all.
   - *As shipped:* deploy-to-dev plus diff disclosure is a hard precondition of the ready-to-test handoff; every landing from F-2 onward carried the deployed-backend section.
   - *Why it changed:* during F-2 the owner's device test failed because the new rules existed only in the local repo while dev Firebase still ran the old ones, costing a full test round. [Owner-approved 2026-08 — "I want to see any cloud and firestore rule changes. I just want them deployed, so I can test and review"; doc gap caught by G44, completeness audit]
4. **Rules-suite landing gate.** The **coordinator**, not the worktree agent, runs `npm run test:rules` (and `npm test`) from `LicensePlateAppiOS/functions` on a Java-equipped shell (`JAVA_HOME=$(brew --prefix openjdk)`) before any rules change is declared landed — the Firestore emulator is a Java jar and worktree agents generally cannot execute it. A feature MUST NOT ship rules cases that were never executed, and no agent may treat rules cases as verified by CI (see §15.3 — there is no CI). [Reviewer-flagged — G57, completeness audit; F-6's rework shipped 8 rules cases unexecuted, citing §15's CI claim]
5. The owner tests and reviews, then either **commits and approves** (next feature lands) or **requests changes** (agent revises in its worktree, re-lands cumulatively — F-6 took four rounds, F-7 three). Agents never commit, and the owner holds approval while a delta is pending.
6. **Hotfix on an uncommitted feature (new).** When a Critical defect is found during owner review of a feature that is landed-but-not-yet-committed, the fix's worktree MUST replicate the **current main working tree including its uncommitted work** as its baseline before it is built or tested. Green tests against a clean base commit prove nothing about the tree the fix has to land in. [Reviewer-flagged — G45, adversarial review of the ads-for-child fix; round 1 was built and green-tested against a clean base while F-8's uncommitted edits to the same five files sat in the real tree, so its passing tests were meaningless and its rename conflicted at landing]
7. Later waves block on committed dependencies. Wave boundaries are hard sync points.

### 2.4 Independent adversarial verification (Critical features)

Any **Critical**-severity child-signal or compliance change MUST be verified before landing by an agent **other than its implementer**. That verifier:

- attempts to construct a failure in **both directions** — a child treated as an adult, **and** an account held in a protected/restricted state permanently with no recovery path;
- **builds and runs the test suites itself** rather than accepting the implementer's report;
- treats an **explicit `false`** signal and an **absent** signal as distinct cases — the absent case MUST NOT clear a cached child flag or the device ratchet (FR-19/FR-39).

Applies to the remaining unbuilt Critical items: OQ-5 (TFCD ads for consented children), D-11 (parental per-child location toggle), and the §18 cross-family-play / parent-reviewed-friendship relaxations. ## §4 Definitions

- **Child** — `users/{uid}.isChildAccount == true`; per policy, under 13. The missing-flag rule is **split by consumer** and MUST NOT be applied flatly:
  - *Originally specified:* one flat rule for every reader — "Missing flag ⇒ **not** a child" (matching missing-`isRegistered`-⇒-registered, `userSearchCore.ts:14-20`, `firestore.rules:22`).
  - *As shipped:* a resolution carries **two bits** — `UserRepository.ChildAccountResolution { isChild, isServerExplicit }` (`UserRepository.swift:70-120`), deliberately two bits and not a tri-state. **Gating** (session posture, ads, server enforcement, rules) reads `isChild`, where an absent key resolves to `false` — required, since a legitimate adult document never carries the key and treating that as unresolved would hold every adult account forever. **Destructive consumers** — anything that retires a uid's child lineage or lifts a device marker (FR-39) — accept ONLY `isServerExplicit == true`, i.e. a key the server literally wrote. Ingest goes through `ingestChildAccountResolution`, so no call site can record a resolution without stating provenance.
  - *Why it changed:* adversarial review of the ads-for-child fix found that several writers create a `users/{uid}` doc with no flag on it; combined with F-8's manager correction, an absent key would have permanently erased a real child's protections with no way to ever re-flag the account — strictly worse than the original bug. An absent key is the absence of evidence, never a manager's decision to un-child an account.
  [Reviewer-flagged 2026-08 — session-audit G5, adversarial review of the ads-for-child fix]
- **Flagless user doc (failure shape)** — a `users/{uid}` document written WITHOUT the `isChildAccount` key is byte-identical to a legitimate adult document and therefore gates as not-a-child. Any writer that can create one ahead of the declaration is a live COPPA hole (FR-27). [Reviewer-flagged 2026-08 — session-audit G2, owner device test]
- **Server-resolved snapshot** — the only snapshot that may resolve the flag. `ChildFlagIngestPolicy.mayIngest(isFromCache:hasPendingWrites:)` (`AgeGateStore.swift:324`) rejects any snapshot carrying `isFromCache` or `hasPendingWrites`: a latency-compensated snapshot shows only the fields the client just wrote, so a missing flag there is the client's own write echo, not a server answer, and the projection stays **nil (held)**. Applied at every ingest site — `UserRepository.swift:144` and `:258` (`loadUserDataFromFirestore`, `refreshUsersFromFirestoreIfPresent` / `mergeRemoteUserDocument`), `UserProfileListenCoordinator.swift:52`, and `FirebaseAuthService.fetchIsChildAccount` (`:1697`), which gates its **return value** as well as the ingest. [Reviewer-flagged 2026-08 — session-audit G6, adversarial review rounds 1-2]
- **Device-declared-child history** — device-local `AgeGateStore.declaredChildUserIds` (`AgeGateStore.swift:28`): the set of uids this device has declared under 13. A third posture input beside the per-uid cache and the device ratchet; consulted before `MobileAds.start()` and outranking any non-fresh server `false`. Cleared per-uid only by a qualifying correction (FR-39). [Reviewer-flagged 2026-08 — session-audit G10, completeness audit]
- **Provisional child** — flag set at registration via `declareChildRegistration` (neutral age screen), no consent record, no active family. Fully protected and restricted (§11.4).
- **Consented child** — flag true + active family membership + `GRANTED` consent record whose consenting manager's family the child is currently in.
- **Unconsented child** — flag true, no active family (provisional or post-exit sticky). Restricted state applies.
- **Correction vs. revocation** — clearing because the person is *not/no-longer under 13* is a **CORRECTION** (protections lift). Ending consent while still a child (removal, family end, withdrawal, deletion) is a **REVOCATION** (protections persist; collection stops). Distinct events, distinct records (FR-5/6, §11.3).
- **Parent / manager** — member-doc `role ∈ {creator, captain}` (`family.ts:138-144, 461-467`; rules 51-61). No MVP path assigns captain ⇒ effectively creator-only (OQ-1).
- **Consent record** — append-only `audit_logs` doc via `writeAuditLog` (`audit.ts:20-42`), client-inaccessible (rules 260-264), retained indefinitely (F-12 carve-out), survives account deletion.
- **TFCD** — `tagForChildDirectedTreatment` on the process-global `MobileAds.shared.requestConfiguration` (SDK 12.14.0; no per-request child API).
- **Projection** — read-only client mirror of server state, never persisted to SwiftData (pattern: `entitlementTagsByUserId`, `UserRepository.swift:26`).
- **Device ratchet** — device-local UserDefaults marker set when any uid on the device has cached `isChildAccount == true`; governs anonymous/signed-out treatment (FR-39). **No longer strictly one-way:** a qualifying manager correction may disengage it under the conditions in the FR-39 amendment. [Reviewer-flagged 2026-08 — session-audit G10, completeness audit]

## §5 Requirements — child signal (FR-1…FR-41, amended per §0)

### Flag set/clear paths

**FR-1** Creator/captain can mark a pending join request as a child at approval: `approveFamilyJoinRequest_CaptainStep` payload gains `isChild: boolean` plus, when true, `consentAcknowledged: true` and `guardianAffirmed: true` (FR-31). `isChild=true` without both acknowledgments ⇒ rejected.

**FR-2** Creator/captain sets child status for an existing member, and clears it **as a correction only**, via `setFamilyMemberChildStatus`. Clearing requires `correctionReason ∈ {flag_set_in_error, child_turned_13}`. No self-targets; no `creator` targets. Consent *withdrawal* is never expressed here — it is removal (FR-6) or parent-initiated deletion (FR-30).

**FR-3 (amended — `declareChildRegistration` carve-out)** All child-status writes are Cloud Functions using `enforcedCallable` (App Check), with `clientMetadata` as sibling field (`.addingClientMetadata()` / `normalizeClientMetadata`). No client writes the flag directly (FR-7/8). Auth gate **by callable**: `setFamilyMemberChildStatus`, `requestChildDataDeletion` and `getParentalConsentStatus` use `assertRegisteredAccount`; **`declareChildRegistration` uses `assertAuthenticated` only, and MUST NOT be tightened.**

- *Originally specified:* every child-status write uses `enforcedCallable` + `assertRegisteredAccount`, with no exceptions.
- *As shipped:* `declareChildRegistration` is `enforcedCallable` + `assertAuthenticated` (`familyChildStatus.ts:64-65`; rationale recorded in the file header, lines 7-12). Safe because the callable is protective-direction-only — it sets `isChildAccount = true` on the caller's own uid and can never clear it — so the weaker gate can only add restrictions.
- *Why it changed:* FR-27 (per G-4) makes the first-launch **guest auto-account** one of the four mandatory age-gate paths. That declaration happens from an anonymous uid *before* any profile write and therefore before any registration; `assertRegisteredAccount` there would dead-end the path and defeat the age gate.

[Reviewer-flagged — G27, completeness audit; the carve-out shipped with F-5a and the SRS never recorded it]

**FR-4** Setting `isChild=true` executes **one batched write**: `users/{childUid}.isChildAccount = true`, `families/{fid}/members/{childUid}.isChild = true`, strip `email`/`phoneNumber` subfields from the child's `linkedPlatforms` (FR-35). **After** the batch: purge all search indexes (`clearAllSearchIndexesForUser`, `userSearchIndex.ts:218-241`), expire pending invites from non-family senders and remove friendship edges (FR-36), write `AUDIT_PARENTAL_CONSENT_GRANTED`. Follow-ons are **not atomic**; the `onUserProfileSearchIndexSync` FR-11 exclusion is the backstop; function must be retry-safe/idempotent. Test pins the backstop (purge failure ⇒ syncer still removes entries).

**FR-5** Clearing (correction) sets both fields false, writes `AUDIT_PARENTAL_CONSENT_CORRECTED` with the chosen reason. Index re-creation via normal profile-sync triggers. The clear dialog presents the two correction reasons and separately signposts "Remove from family" / "Remove and delete data" as the paths for ending participation of someone still a child.

**FR-6** When a flagged child's membership ends by any path — `removeFamilyMember` (`family.ts:672`), `inactivateFamily` (`family.ts:841-845`), `deleteAccount` inactivate branch (`accountDeletion.ts:146`), `deleteAccount` remove_member branch (`accountDeletion.ts:157-159`, which gains its missing audit), `onAuthUserDeleted` (`auth.ts:60`), `requestChildDataDeletion` (FR-30) — write `AUDIT_PARENTAL_CONSENT_REVOKED` with the appropriate reason. `isChildAccount` **stays true** (sticky); account enters restricted state (FR-28): protection persists, collection stops.

### Rules hardening

**FR-7 (amended — create-time twin + merge-write contract)** No client may change **or introduce** `isChildAccount`.

  *Originally specified:* one update-time diff-guard — generalize `userDocPreservesEntitlementTags` into `userDocPreservesServerControlledFields()` (rules ~101-104), rejecting writes whose `affectedKeys()` include `entitlementTags` or `isChildAccount`.
  *As shipped:* that guard plus a create-time twin `userDocCreateOmitsServerControlledFields()` (`firestore.rules:108`, applied at `:164`), rejecting any `users/{uid}` **create** whose `request.resource.data.keys()` contain either key.
  *Why it changed:* a create has no `resource.data` to diff against, so the update-time guard is vacuous on the first write — a self-registering client could smuggle either key in at account creation. Logical hole in the original text, found during F-5a/F-6 rules work. [Reviewer-flagged — G13, completeness audit]

**Client write contract (normative):** client writes to `users/{uid}` MUST use merge/update semantics. A full `setDoc` that drops `isChildAccount` is DENIED by the diff-guard — the same contract `entitlementTags` already imposed. §15.2's "the diff-guard blocks fields no client writes" holds for field *values*, not for write *shape*. [Reviewer-flagged — G13, completeness audit]

**FR-8** Member-doc client writes (rules 233-238) become `allow create, update, delete: if false;` (read unchanged). All mutations already flow through callables; `FamilyMember.toFirestoreData()` is unused by the shipped client — zero regression.

### Discoverability — child as target

**FR-9** A child never appears in any `searchUsers` result (username/email/phone, including the direct `userNameLower` prefix query, `userSearch.ts:103-124`). Enforced at the single choke point `toPublicSearchHit` (`userSearchCore.ts:88-116`).

**FR-10** `isContactSearchableFromUserData` (`utils/validation.ts:100-135`) returns false for a child (also covers the `sendFamilyInvite` privacy gate, `family.ts:175-194`).

**FR-11** Index syncers (`userSearch.ts:189-330`) treat a child like a non-registered user: never create `usernames` / `user_lookup_email` / `user_lookup_phone` entries; flag-set purges retroactively (FR-4); provisional children never get entries (FR-27).

**FR-12** Peers cannot read a child's `users/{uid}` doc except family members. `isDiscoverableUserProfile` (rules 19-23) becomes, in exactly this order (child check first; key-presence guard before path construction):

```
existing checks
&& ( resource.data.get('isChildAccount', false) != true
     || ( 'activeFamilyId' in resource.data
          && exists(/databases/$(database)/documents/families/$(resource.data.activeFamilyId)/members/$(request.auth.uid)) ) )
```

Emulator matrix: orphaned child denied to everyone including ex-family; adult without `activeFamilyId` still readable; family member reads child; anonymous denied. Bare `list` queries not provable under the carve-out — acceptable (live client fetches by uid; callable path filters children).

## §11 Consent record, parent rights & lifecycle

**11.1 Record shape** (via `writeAuditLog`): `eventType` ∈ the four new types; `actorId` = parent uid (or exiting/deleted uid on background paths — reason carries provenance); `subjectType: "user"`, `subjectId` = child uid; `metadata` (uid-only, **no PII ever**): `{familyId, childUserId, actorRole, consentScope: ["gameplay","search_excluded","analytics_limited"], policyVersions, consentTextVersion, affirmationVersion, guardianAffirmed, expectedAgeOutYear?, method, reason?, removedFriendEdgeCount?}`. **Location and ads are deliberately absent from `consentScope`** — all location flags are forced off (FR-33) and child sessions see no ads (FR-19). `clientMetadata` sibling via `normalizeClientMetadata`; omitted on background triggers.

**11.2 Why `audit_logs`:** client-inaccessible, append-only, survives account deletion, and — with the F-12 carve-out — exempt from retention cleanup. With FR-35 landed (no plaintext email anywhere in audit metadata or logs), a uid-only record becomes **pseudonymized** once `users/{uid}` and `private/*` are deleted — not anonymized: the uid remains a stable identifier, `auditValueHash` is an unsalted truncated SHA-256, and the deletion tombstone is a deterministic per-uid derivation (§16 hash-strength row; project salt is a §18 follow-up). [Reviewer-flagged — G34, adversarial review] Never copy the `familyName`-in-metadata precedent; if parent-contact evidence is ever required, use the hashed `ipHash`/`deviceIdHash` slots, never plaintext.

**11.4 State machine:** `age-unknown guest` (**no uid provisioned**, restricted, never prompted — the state a device sits in after sign-out or account deletion, D-17/FR-27) → *(age screen, 13+)* → `adult`; `age-unknown guest` → *(age screen, under-13)* → `provisional child` (restricted) → *(family admission + consent)* → `consented child` → *(correction)* → `adult`; or → *(removal / family end / withdrawal)* → `restricted child` → *(re-admission FR-25)* → `consented child` or `adult`; or → *(deletion FR-30/40)* → gone. The pre-flag exposure window is closed for self-registered children by FR-27; FR-4 purge + FR-36 cleanup remain the belt-and-braces path for children flagged later by a parent.

**11.5 Parent review & deletion:** FR-29 + FR-30 deliver the Privacy §12 promises; the child can also self-delete (FR-40). No standing deletion clock in MVP — withdrawal stops collection immediately (FR-28); deletion is offered at removal.
